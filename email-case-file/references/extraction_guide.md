# 判讀規則

這份文件說明如何從信件中判斷「已決策」、「尚未決策」、「待辦」、「已完成」，以及如何給信心程度。背景：使用者是健身器材製造商的主管，信件多半是和外銷客戶、供應商、公司內部同事的往來，常中英文混雜。

## 人物與拍板權

報告的核心是「誰在什麼時候決定了什麼」，所以先搞清楚誰是誰。

- **合併同一個人**：同一人常有多個 email（公司、個人）和多種名字寫法（「王大明」「David Wang」）。`people.json` 只能依位址和顯示名稱自動合併；中英文名字的對應要靠簽名檔和信件內容判斷，不確定就放進人物表請使用者確認，不要自己斷定。
- **判斷拍板權**：看簽名檔職稱與信中行為。採購、PM、部門主管、老闆通常可拍板；助理、業務窗口、轉達訊息的人通常不可。對方有沒有拍板權會直接影響決策的信心程度（見下一節）。
- **人物表寫進 `people`**，增量整理時沿用。上次已確認的人（`people.json` 裡有 `confirmed`）不要重問，只確認新出現的人。
- 同一人用不同位址寄信（例如公司信箱轉個人信箱），決定者填同一個名字。

## 增量整理時的判讀

資料夾已有上次報告時，新信可能「改變」舊結論，要逐項檢查：

- **新信解決了舊的未決議題**：把該條從 `pending` 移到 `decisions`，`note` 寫「解決 E0xx 提出的問題」。
- **新信推翻舊決策**：兩條都保留，後者 `note` 寫「推翻 YYYY-MM-DD 的決定」（規則同「決策被推翻」）。
- **新信顯示待辦完成**：從 `todos` 移到 `completed`，`evidence` 寫明依據。
- **舊待辦到期了仍沒動靜**：保留在 `todos`，腳本會自動顯示「已逾期」並列入「剛逾期」。不要自己改成已完成。
- **沒有受影響的條目**：整條原樣保留，包含 `key`（腳本靠 `key` 認出新舊報告裡的同一條）。舊條目有更新時改內容、`key` 不動；新條目不填 `key`。
- 舊信的 `source.id` 不會變；新信的編號接在最大的舊編號後面，所以新信不一定是編號最大的時間順序，以 `date` 為準。

## 已決策事項

決策是「某件事的方向被有權限的人定下來了」。

**常見的隱性拍板說法**

- 英文：OK / Go ahead / Approved / Confirmed / Let's go with... / Please proceed / We accept / Agreed / That works for us
- 中文：就這樣 / 照這個做 / 確認 / 同意 / 可以，就出吧 / 以此為準 / 沒問題就下單

**判斷決定者是否有權限**

拍板的效力取決於說話的人。同一句「可以」：

- 客戶的採購、PM、老闆說 → 通常是正式決策（信心：高）
- 我方業務轉述「客戶說可以」 → 二手資訊（信心：中），記下「據某某轉述」
- 對方承辦人說「我個人覺得可以，再跟主管確認」 → **不是決策**，列入尚未決策

不確定對方職稱時，先查人物表，再看簽名檔；還是不知道，就寫「職稱不明」並把信心降一級。

**原文關鍵句**

- 摘錄最能證明這個決策的那一句，保留原語言，不翻譯，不改寫。
- 長度控制在一兩句。整段貼上反而讓人找不到重點。
- `decision` 欄位才是你用中文寫的決策內容摘要。

**決策被推翻**

後面的信如果改變了先前的決策（例如 9/5 定 B 方案，9/18 改成 C 方案），兩條都要保留，並在後面那條的 `note` 寫明「推翻 9/5 的決定」。開會時「原本定什麼、後來為什麼改」往往正是要討論的事。

## 尚未決策的議題

有人提出問題或方案，但還沒有人拍板。常見樣態：

- 提了方案，沒人確認（「附上兩個配色，請選擇」之後沒下文）
- 問了問題，沒人回覆（「包裝尺寸可以改成 ... 嗎？」）
- 對方說要內部討論（「Let me check with my team」）
- 有人說「原則上可以」但附帶條件還沒談妥

`raised_date` 填**問題最早被提出的日期**，不是最後一次追問的日期；腳本會算出懸而未決幾天。如果中間有人追問過，寫在 `note`，例如「9/10 業務追問一次，仍未回覆」。

`waiting_on` 寫清楚球在誰手上，例如「客戶（John, 採購）」或「我方研發（王工程師）」。這是開會時最需要知道的一欄。

## 待辦事項

- 有人承諾要做的事：「我下週寄樣品」、「I'll send the revised drawing by Friday」
- 被要求做、且沒有拒絕的事：「請於 9/30 前提供測試報告」

期限要換算成實際日期。「下週五」要依那封信的寄件日推算，並在 `due` 填日期。推算的期限信心降一級。

已經看到完成跡象的，改列在「已完成」，不要重複列在待辦。

## 已完成事項

幾乎不會有人明寫「完成」，要看間接證據：

| 證據 | 信心 |
|---|---|
| 對方明確回覆「收到」、「確認無誤」 | 高 |
| 出貨通知、船期、提單號碼 | 高 |
| 信中附上了承諾的檔案（例如「附件為修改後圖面」） | 中（附件寄了，不代表對方接受） |
| 之後再也沒有人提起這件事 | 低（可能完成，也可能被遺忘），列為「待確認」 |

`evidence` 欄位寫明是哪種證據。

## 信心程度

| 等級 | 意思 |
|---|---|
| 高 | 信中有明確文字支持，而且說話的人有權限 |
| 中 | 有文字支持但需要一點推論（轉述、推算期限、只看到附件已寄） |
| 低 | 主要是推論（沒人再提、語意模糊），報告中會標「待確認」 |

## 附件

開發案、報價案的關鍵變更常常只在附件裡（單價、數量、規格、交期），信件本文只寫「修正如附」。

**沒有用 `--read-attachments`**：只記錄附件檔名。檔名看得出版本（`spec_v3.pdf`、`報價單_修正2.xlsx`）就在時間軸點出「第幾版」，並註明「附件內容未讀取」，不要猜附件裡寫了什麼。

**有用 `--read-attachments`**：`emails.txt` 每個附件會有摘錄、全文檔案路徑，以及同系列附件和前一版的差異。判讀方式：

- **先看差異，再讀全文**：有 `與 E0xx《…》相比` 的，差異預覽通常就是重點；差異太長或看不出全貌時，才用讀檔工具讀 `全文` 或 `完整差異` 檔。沒有差異的附件只看摘錄，不要把每個附件全文都讀進來。
- **哪些附件值得讀全文**：報價單、規格書、PO／訂單、合約、圖面清單、測試報告。簽名檔圖片、型錄、宣傳 PDF 看摘錄就好。
- **數字與規格的變更一定要寫進 `attachment_notes`**，例如「單價 USD 120 → 125」「數量 100 → 150」。這是開會最常被問到的事。
- **決策出自附件**：例如客戶在回信寫「如附件確認」，附件是簽回的報價單。決策的 `source.attachment` 填附件檔名，信心依內容判斷：附件內有明確簽認、數字與我方一致 → 高；只是附上檔案沒有表態 → 中以下。
- **重複附件**：回覆串常把同一個附件再寄一次，狀態會是「內容相同，不重複讀取」，不要把它當成新版本或新動作。
- **讀不到的附件**：掃描 PDF（無文字層）、圖片、CAD（.dwg）、過大的檔案，狀態會寫原因，原檔存在 `attachments/` 裡。掃描 PDF 或圖片重要時，用讀檔工具直接看原檔（圖片）或告訴使用者「這份附件需要人工查看」，不要編內容。缺套件會列在腳本輸出，請使用者安裝後重跑。
- **版本差異只是文字比對**：同系列判斷靠檔名（去掉 v1、修正2、日期等字樣後相同）。兩份不同批次的同名檔（如每次出貨的 Packing List）也會被比，所以報告裡寫「與前一份相比」，不要斷言「版本升級」，除非信件內容佐證。

## 時間序報告

每封有實質內容的信一條，欄位與寫法見 SKILL.md「時間序條目」。補充判讀：

- `points` 寫「這封信推進了什麼」，不是複述全文；數字、規格、日期的變更一定要留。
- `actions` 只收信中明確提到的待辦（承諾、被要求）；負責人與期限沒寫就空著，不要猜。
- 純禮貌、只有「收到，謝謝」的信可以合併或略過，但如果它是某件事完成的證據，要保留。
- 依時間由舊到新排序。
- **長信**：`emails.txt` 標「內文過長」的信只列了前 8,000 字，全文在它寫出的 `bodies/E0xx.txt`。先把全文讀完再寫這封信的條目；`quote` 可以取自全文的任何位置，腳本核對時也是比對全文。
- **引用拆出來的信（`src: "quote"`）**：和一般信一樣逐封寫，`id` 用它自己的編號，不要再用收錄它的那封（`container`）。它沒有附件資訊；附件要看 `container` 那封。
- **純轉寄信**（`body` 空白或只有「FYI」）：它本身沒推進什麼，但「誰在什麼時候把這串轉給誰」可能是重點（例如通報主管）。有這個意義就寫一條，否則略過。
- **時間推估**：引用信的時間是從標頭推的（`date_approx`）。同一天內兩封信的先後若影響判斷（例如誰先讓步），回原信確認，不要只靠排序。

## 數字演變（figures）

- 每次有人寫出一個新的數字（提出、還價、重算、接受），就記一版。只是引用或重複上一版的數字不用記。
- `value` 照原文寫，含幣別；US$ 和 € 混用時不要自己換算，在 `note` 註明「幣別與前版不同」。
- `status` 依說話者身分判斷：不可拍板的人（業務、助理）轉述的「對方應該會接受」只能算 `提出` 或在 `note` 註明是轉述，不能填 `接受`。
- 同一個數字被分成幾個部分時（例如 40,000 = 今年付 20,000＋明年折讓 20,000），拆成獨立的組，或在 `note` 寫清楚組成。
